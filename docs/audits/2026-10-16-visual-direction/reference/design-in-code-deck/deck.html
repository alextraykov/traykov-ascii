How it worked on Bebop 2

  me + Claude Code               huey repo
  ┌────────────────┐  branch   ┌──────────────────┐
  │ "add press     │ ────────▶ │ libs/bebop2-     │
  │  feedback to   │           │   components     │
  │  Button"       │           └────────┬─────────┘
  └────────────────┘                    │ PR
                                        ▼
  ┌──────────────────┐         ┌──────────────────┐
  │ Storybook review │ ◀─────── │ CI   │
  │ plain · reduced  │         └──────────────────┘
  │ slow · light/dark│
  └────────┬─────────┘
           │ engineers review
           ▼
  ┌──────────────────┐
  │ Radoslav, Marin  │ ────────▶  merged ✓ × 0
  │ tests, keyboard  │
  └──────────────────┘

I write the change with Claude. Claude handles the branch, the PR and the CI fixes.

Engineers review it like any other PR. They asked for tests and raised a keyboard point. That made the work better.

Review happens in Storybook, in plain, reduced-motion and slow-motion modes, light and dark.

Nine motion PRs merged. For example QDS-78, press feedback on Button and pagination.

Harder parts: an OpenSpec and approval process, and CI runs only Jest, so lint and typecheck are by hand.

I run the production repo locally, against my own realm, with the real components.

I build prototypes there and open PRs, for example the model picker and restyle fixes.

Prototypes are hosted on a private GitHub Pages site. Each one comes with markdown specs for engineers.

Harder parts: local setup, Jenkins and manual deploys, a very long CLAUDE.md, and eight code owners with no designer among them.

    is mine?"       write the       GitHub
                    copy?"          seat"

  not hosted on a website ──▶ it got lost

No Figma frames meant friction for content designers and PMs. Content had no easy place to see the design and write the copy for it.

They needed GitHub access to see anything in a repo.

If I didn't host a prototype on a website, it got lost.

Figma is clearer about what the deliverable is: one set of frames per feature. My suite showed the whole experience, so engineers weren't sure what to focus on.

Three options

Same direction, different cost. A designer can move from one option to the next when they are ready.

option 1   git [░░░]

HTML files + README

who
Everyone, from day one
output
A clickable HTML prototype with intent, motion and delight, a states page, and a README with build instructions
engineers
Build from it
needs
Claude Code. No GitHub seat.
option 2   git [██░]

Work in the repo

who
Designers with access and a working local setup
output
Design examples running locally with real components. PRs as support for engineers
engineers
Take the PR as it is, or adapt it
needs
GitHub seat, setup guide, one engineer buddy. This is how I work on Pave now.
option 3   git [███]

Full design engineering

who
A few people who want it
output
Production UI: components, states, motion, shipped
engineers
Review and merge. They own logic and data
needs
All of option 2, plus the design system in code, CI checks and a review agreement

Designers run the product locally and build design examples with the real components.

The PR supports the engineer. It is a strong suggestion, not the final code. Engineers decide what to keep.

Claude handles the git work. The designer reviews the diff and the preview.

Needs: GitHub seats (still blocked), a setup guide that works, and one engineer buddy per repo.

Designers own the UI layer in production. Engineers own logic and data, and review every PR.

This is the Bebop 2 motion work at a bigger scope.

Only for a few people, and only when the design system is complete in code and CI checks the basics.

Needs: everything in option 2, plus an agreement with engineering on what designers can merge into.

Friction we should expect

  $ open prototype --as content-designer
  ✗ 404  no GitHub seat
  $ open prototype --as pm
  ✗ 404  no GitHub seat
  $ find prototype "nav v2"
  ✗ not found. it was never hosted
  $ engineer --what-do-i-build
  ✗ unclear. one suite, nine features
  $ content --write-copy
  ✗ no frames to write next to
  $ setup --new-designer
  ✗ days, not hours: seat, local env, realm
  $ review --ai-code
  ✗ pushback. see next slide
  $ claude-design --open
  ✗ closes 14 Dec 2026

These will happen. Most of them already happened on Pave.

Option 1 avoids the access errors, because an HTML file opens anywhere.

Options 2 and 3 hit all of them. Setup and seats cost days per person, and the review friction grows with the size of the PR.

Planning for these is part of the work. Nobody should be surprised by them.

friction

Engineering pushback on AI code

  PR  design support: press feedback on Button
  ┌──────────────────────────────────────────────┐
  │ eng  was this written by AI?                 │
  │ eng  explain the render cycle here           │
  │ eng  why not useMemo? what about SSR?        │
  │ eng  this isn't how we'd do it               │
  │                                              │
  │ designer  the motion and states are the      │
  │           point. the code is a suggestion.   │
  └──────────────────────────────────────────────┘
  [!] the review is about the designer,
      not about the design

Engineers can be defensive about AI code. Some are dismissive when the deliverable is AI-written.

Some press designers on engineering topics, because we now deliver in code. It is not productive, and it happens.

It makes designers stop. One bad review and people go back to Figma.

This needs a manager-level agreement with engineering leads before we start: what a design PR is, what reviewers judge, and what they don't.
